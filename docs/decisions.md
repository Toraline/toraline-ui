## 2026-11-16 - Fixes found when Intraweb installed the library, version 0.3.1 (TOR-1223)
- Context: the app Intraweb installed version 0.3.0 (pull request 108 of `prontera-e-juno`) and compared 279 screenshots taken before and after. The rule of the project: Intraweb looks and behaves the same with the library, except an accessibility fix made on purpose. The comparison found bugs that Intraweb works around, and visible differences that earlier entries of this file record as known. Each item below is one of them.
- How each item was checked: a temporary page outside both repositories rendered Intraweb's own component files of before the library (`apps/intraweb/src/components/ui/`, branch `staging` of `prontera-e-juno`, with its `globals.css`, its theme files and its Inter and Poppins files) next to a second page with the source of `packages/ui` and `packages/tokens` of this branch. A Playwright script (Chromium with no window) read the measures and the computed styles of both pages, in the light and the dark theme, at 1280 and 390 pixels wide, and with the text sizes 90%, 100%, 115% and 130%. The page and the script are not committed.
- Item 1, Field, the mark of an optional field. The space before the mark was outside the mark's `<span>`, so it had the weight of the label (500), which is wider than the weight of the mark (400): the text "(opcional)" was about 0.3 pixels to the right of where Intraweb draws it. Decision: the space is inside the `<span data-slot="optional">`, and a mark that is a text is one piece of text with its space (`" (opcional)"`), which is Intraweb's markup. Checked: the position and the width of the mark are equal to Intraweb's at every width, theme and text size. The name a screen reader gets is unchanged: Chromium computes "Nome (opcional)" for both.
- Item 2, Field, a child that is not the control. Field copied its child with `id`, `aria-describedby` and `aria-invalid` whatever the child was. With `<Field id="x"><div><TextInput id="x" /></div></Field>` the `<div>` got `id="x"` too: 2 elements with one id, and a click on the label did not move the focus to the field. Intraweb has 20 such Fields (16 with its Markdown editor, 2 with a `<div>`, 2 with its category select) and works around it in its own `field.tsx`.
  - Decision: Field gives the 3 props only to a child that is the control: a component, or one of the native elements a `<label>` can point to (`input`, `select`, `textarea`, `button`, `meter`, `output`, `progress`). For any other child (a `<div>`, a fragment, several children) Field looks inside the native elements and the fragments for the element whose `id` is the id of Field, and gives `aria-describedby` and `aria-invalid` to that element. It does not look inside a component. When no element has that id, nothing is copied.
  - Why: Intraweb's usage is the same id on Field and on the control, so all 20 Fields work with no change and no workaround, and the 2 Fields with a `<div>` also get the hint and the error message linked, which the workaround did not give them. A component as the direct child still receives the 3 props, as in 0.3.0: Intraweb's Markdown editor and category select take `id` and ignore the other 2. Field still needs no `"use client"` (the reason of the entry of TOR-1141 against a React context holds).
  - This replaces, in the entry of TOR-1141: "A Field whose child is a wrapper element (not the control) must give a function, or the wrapper gets the 3 props". The function still works and is still the way for a control with no id of its own.
  - Not a breaking change for a correct usage. One usage changes: a `<div>` that was the direct child and has no element with the id of Field inside no longer receives `id`, `aria-describedby` and `aria-invalid`. Those attributes on such a `<div>` were the bug.
  - Checked in the temporary page: with a `<div>` around the control, one element has the id, a click on the label moves the focus to the field (as in Intraweb before the library), and the field has `aria-describedby` with the id of the hint (Intraweb before the library: no `aria-describedby`; the link is the accessibility fix of TOR-1141).
  - Alternatives: a React context that the controls read (needs `"use client"` in Field and in every control); copying only a known list of the library's controls (a component of an app would get nothing); giving the 3 props to the first native control found inside (wrong when a button comes before the field).
- Item 3, Popover, `autoFocus` inside the panel. The panel had the class `invisible` (the CSS `visibility: hidden`) until it was measured and placed. React gives the focus to an element with `autoFocus` when the element is added to the page, which is before the panel is placed, and a browser refuses the focus on an element that is not visible. So `<Popover><input autoFocus /></Popover>` left the focus on the button; in Intraweb before the library the field got it. Intraweb works around it in `item-picker.tsx` with a `ref` that waits one frame.
  - Decision: the panel that is not placed yet has `opacity-0` in the place of `invisible`. It still cannot be seen, and it can get the focus, so `autoFocus` works with no code. The panel is placed before the browser paints (a layout effect), so neither class is ever painted.
  - Why not a new prop (`initialFocus`): `autoFocus` is what Intraweb's screens already write, and it is the HTML way. A prop would be a second way to say the same thing.
  - Not changed: ActionMenu and the filter panel of the DataGrid keep `invisible`. They move the focus themselves after the panel is placed.
  - Checked in the temporary page: after a press on the button the focus is on the field, in Intraweb before the library and in the library. The story "Focus On Open" checks it in Chromium in both themes; with `invisible` put back, that story test fails.
- Item 4, DataGrid, the field that chooses the number of rows of a page. The library drew it 80 pixels wide (`w-20`). Intraweb writes `w-20` too, but in Intraweb that class loses to the `w-full` of its Select (item 12), so its field is as wide as its content: 74 pixels with the sizes 10, 25, 50 and 100. Intraweb works around it with a `selectComponent` that adds `w-full`.
  - Decision: the grid gives the field the class `w-full` in the place of `w-20`. `selectComponent` now receives `className="w-full"`.
  - Checked in the temporary page: the field is 74 pixels wide and at the same place as Intraweb's, at 1280 and 390 pixels, in both themes.
- Item 5, the line height when the text size of the page is not 100%. Intraweb lets a person choose a text size of 90%, 100%, 115% or 130% (the font size of the root element). At 115% some lines of text were 1 pixel higher or lower than before the library.
  - The cause, measured in the temporary page at 115% (root font size 18.4 pixels, `text-sm` 16.1 pixels): Intraweb writes `text-sm`, whose line height is a ratio of the font size with no unit (`calc(1.25 / 0.875)`, Tailwind's value). The box of a line is 22.984375 pixels high: 16.1 times 1.428571 is a little less than 23, and Chromium keeps a layout length as a multiple of 1/64 pixel and cuts this one down. The library wrote `text-sm/5`, whose line height is a length (`calc(var(--spacing) * 5)`, 1.25rem), exactly 23 pixels. The difference, 0.015625 pixels for each line, adds up down the page until one line lands on another pixel. The same happens with `text-xs` (18.390625 and 18.40625 pixels at 115%). At 100% both forms give 20 pixels. Why Chromium cuts the first value down was not checked in its source code; the numbers are the ones measured.
  - A second effect of the same cause: a ratio is inherited as a ratio, so a text inside the element with another font size gets a line height for its own size. A length is inherited as that length.
  - Decision: a component writes a font size the way Intraweb's component writes it. Where Intraweb writes the size alone (`text-xs`, `text-sm`, `text-base`, `text-lg`), the library now writes the size alone: 41 classes in 23 files. Where Intraweb uses a text style, whose line height is a length in `rem` (`label`, `label-sm`, `heading-card`, `heading-section`, `caption-overline`, `display-number`), the library keeps the size with a spacing step (`text-sm/5`, `text-xs/4`, `text-base/6`, `text-lg/7`, `text-2xl/8`, `text-3xl/10`): 15 classes. A component with no Intraweb component of the same name (Toggle, BreadCrumbs, SplitButton) has the size alone, as the Intraweb component it looks like (Checkbox, Button).
  - Decision (the preset of the tokens): `packages/tokens/css/tailwind.css` has a new `@theme inline` block with the line height of the 4 sizes (`--text-xs--line-height: calc(1 / 0.75)`, `--text-sm--line-height: calc(1.25 / 0.875)`, `--text-base--line-height: calc(1.5 / 1)`, `--text-lg--line-height: calc(1.75 / 1.125)`), which are Tailwind's own values. `inline` makes Tailwind write the ratio into the class: `line-height: var(--tw-leading, calc(1.25 / 0.875))`.
  - Why this is sound: the reason of the entry of TOR-1138 for `text-sm/5` was that plain `text-sm` reads Tailwind's variable `--text-sm--line-height`, which is not a token, so the test of the token rule failed. With the block the class reads no such variable, and the test passes unchanged. A ratio has no unit, so the rule "no length in `rem`" holds. `classNames` already treats `text-sm` as a font size. For an app, its own `text-sm` has the same computed value as before; only the text of the built CSS changes. An app that sets `--text-sm--line-height` in its own `@theme` after the preset still wins.
  - This replaces, in the entry of TOR-1138: "a font size is written with its line height as a spacing step".
  - Checked in the temporary page, at 90%, 100%, 115% and 130%, at 1280 and 390 pixels wide: the height and the top of every element with text of Field, TextInput, DecimalInput, Select, Textarea, Checkbox, Button (3 sizes), Panel, StatCard, EmptyState, ListItem, ProgressBar, DetailPanel, Tooltip, StatusBadge and 3 DataGrids (with pages, with rows inside a row, with a view) are equal to Intraweb's. Before the change, 66 boxes of Field and the DataGrid had another height at 115%.
  - Not checked against Intraweb at these text sizes: Modal, Drawer, DiscardConfirmation, DeleteOverlay, ActionMenu, the filter panel and the cell editors of the DataGrid, ListItem as a link, Toggle, BreadCrumbs, SplitButton, Tabs, TabNav. Their classes were changed by the same rule, from Intraweb's source.
  - Alternatives: the ratio written in each class (`text-sm/[calc(1.25/0.875)]`, as one class of DataTable already does), which needs no change of the preset and makes 41 long classes; leaving it, with the reason recorded.
- Item 6, DataGrid, the edges of the letters of "Mostrando 1–25 de 36" and "1 de 2" (53 screenshots). Intraweb writes each of these texts in pieces (`Mostrando {first}–{last} de{" "}{count}` is 7 pieces of text), and a browser shapes each piece by itself. The library received one text from the label function, and the same letters were 0.03 pixels narrower in all, which moved the edges of some letters. The text of the selected rows ("1 selecionado") has the same cause.
  - Decision: the labels `selectedCount`, `pageRange` and `pageOf` may return elements (`ReactNode`), not only a text. An app that gives the pieces Intraweb wrote gets Intraweb's letters. The English defaults stay one text. The library cannot make the pieces itself: where a sentence is cut depends on the sentence.
  - Not a breaking change: a function that returns a text is still accepted.
  - Checked in the temporary page, with the 3 labels written in pieces: the width and the place of both page texts are equal to Intraweb's at 1280 and 390 pixels, in both themes and at 115%, and in a screenshot of the page controls no pixel of the 2 texts differs. (At 1280 pixels in the light theme, 157 pixels differ in the top 2 rows of that screenshot, over the buttons: the faint shadow of the table above, recorded in the entry of TOR-1164.)
  - What Intraweb does to remove the difference: write these 3 labels in pieces in its `data-grid.tsx` (the README of the package has the exact code).
- Items 7, 8 and 11, three colors that Intraweb keeps the same in every theme. They are one commit, because they have one cause and one fix. In 3 places a component of Intraweb writes a level 1 color in a class, and a level 1 color does not change with the theme. A component of the library may use only level 2 tokens (a test checks it), so each place had the nearest level 2 token, which is equal in the light theme and another color in the dark theme:

  | Item | Where | Intraweb's class | Intraweb, both themes | Library before, dark theme | Screenshots that differ |
  |---|---|---|---|---|---|
  | 7 | The small bar at the top of a Modal shown as a sheet | `bg-slate-300` | `#d0d5dd` | `#414651` (`--border-strong`) | 6 |
  | 8 | The dot of a neutral StatusBadge | `bg-slate-400` | `#98a2b3` | `#61646c` (`--text-muted`) | 4 |
  | 11 | The ring of a CheckboxControl with `changed` | `ring-orange-200` | `#fedf89` | `#93370d` (`--border-warning`) | None in the 279 (found in phase 8) |

  - Decision: 3 new level 2 color tokens, each with the same value in the light and the dark theme: `--bg-handle` (`var(--color-slate-300)`, class `bg-handle`), `--data-neutral` (`var(--color-slate-400)`, classes `bg-data-neutral` and the others of the data group) and `--border-changed-ring` (`var(--color-orange-200)`, written `ring-(color:--border-changed-ring)`, as the ring was written before). There are now 62 color tokens and 81 level 2 tokens.
  - The names follow Intraweb's: the group first (`bg`, `data`, `border`), then the part. `--data-neutral` is next to `--data-success`, `--data-warning` and `--data-danger`, which color the dots of the other variants. `--border-changed-ring` is next to `--border-changed`, the border of the same box, which also has one value in both themes.
  - Why tokens and not an exception to the rule: the rule "a component uses only level 2 tokens" stays whole and its test is unchanged, and a theme of an app can give these 3 parts its own colors. None of the 3 differences was an accessibility fix: the entries of TOR-1158, TOR-1150 and TOR-1149 give only the rule as the reason.
  - No value of an existing token changed. The tests that compare the color tokens with the copies of Intraweb's theme files leave the 3 names out (`packages/tokens/src/intraweb-fixtures/added-color-tokens.ts`) and check that each one has the level 1 color of Intraweb's class in both themes. Intraweb's themes `cozy`, `old` and `glass` do not give these tokens, so they get the values of the theme they start from, which are Intraweb's values.
  - Contrast: the 3 parts are decoration (nothing is done with the bar; the text of the badge says the state; the orange border `--border-changed` marks the change too), so no limit applies. Recorded in `packages/tokens/src/tokens.test.ts`: the bar on `--bg-surface` 1.47 (light) and 11.69 (dark, before 1.82); the dot on `--bg-muted` 2.32 and 5.51 (before 2.4); the ring on `--bg-surface` 1.3 and 13.23 (before 2.29).
  - Checked in the temporary page, in both themes at 1280 and 390 pixels: the computed color of the bar, the dot and the ring are equal to Intraweb's, and a screenshot of each part has no pixel that differs.
  - To do by a person: the Figma file "Toraline UI Package" has a collection of variables that mirrors the tokens. The 3 tokens must be added there. Figma was not changed.
  - Alternatives: allow these 3 level 1 colors in the test of the token rule; keep the differences, recorded as known.
- Item 9, DataGrid, the cells of the rows inside a row on a phone (2 screenshots). On a screen less than 768 pixels wide the library showed the name of the column before the value of each cell of an item (`data-label` on the cell), and the page was 43 pixels higher. Intraweb shows only the value.
  - Decision: the cells of an item have no `data-label`. The look is Intraweb's.
  - Why it does not stay: it was not an accessibility fix. The entry of TOR-1213 gives no accessibility reason, and a screen reader gets the names of the columns either way: the header of the inner table is hidden from the eye only, not from a screen reader. For a person who sees the screen the names were a help, so this decision makes the phone look of the library a little poorer in order to keep Intraweb equal.
  - Checked in the temporary page at 390 pixels, in both themes, with a row open: no cell has `data-label`, and a screenshot of the grid has no pixel that differs from Intraweb's.
  - Alternatives: keep the names (Intraweb then differs in 2 screens); a field of `subRows` that turns the names on, which no screen asks for today.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - `homepage` of the two packages is the online catalog (TOR-1196)
- Context: the catalog is online at https://toraline-ui.vercel.app/. `homepage` of `packages/ui/package.json` and `packages/tokens/package.json` was the folder of each package on GitHub.
- Decision: `homepage` of both packages is `https://toraline-ui.vercel.app/`. The address is also in the root `README.md` and in the README of each package, in both languages.
- Why: the page of a package on npmjs.com shows 2 links, "Repository" and "Homepage". "Repository" already opens the folder of the package on GitHub (`repository.directory`), so a `homepage` with the same folder repeats it. The catalog is what a person who looks at the package wants to see next: every component, every token, and the guide.
- Both packages name the first page of the catalog. A link to one page of it (for example the tokens page) breaks when a story is renamed.
- When it shows: npmjs.com reads `homepage` from a published version. The change is visible from the next version on. No version number changed in this ticket.
- Risk: `toraline-ui.vercel.app` is the address that Vercel gives by default. If the catalog moves to another address, `homepage` and the 6 README lines change with it.
- Checked on 2026-11-15: the address answers with status 200 and the page of Storybook. Not verified: who deploys it, and from which branch.
- Alternatives: keep the GitHub folder as `homepage` and name the catalog only in the READMEs; a custom domain for the catalog before any link is written.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - The Portuguese README of each package is inside the published package (TOR-1182)
- Context: the page of a package on npmjs.com shows only `README.md`. The question was where a person finds `README.pt-BR.md`.
- Decision: `README.pt-BR.md` is in the tarball of each package, and line 3 of the English `README.md` links to the Portuguese file on GitHub with its full address. So a person on npmjs.com reaches it with one press, and a person with no network reads it in `node_modules`.
- Why it is cheap and safe: npm puts every file whose name starts with `README` in a package by itself (checked with `npm pack --dry-run`, npm 11.12.1). `files` of the two `package.json` files did not change. `scripts/check-packages.mjs` now fails when `README.pt-BR.md` is missing from a tarball, as it already did for `README.md`.
- Cost: the tarballs grow by the size of one more README. The sizes before and after are in the pull request of TOR-1129.
- Alternatives: keep the Portuguese file out of the package (a `.npmignore` file or a negated entry in `files`) and only link to GitHub, which saves the size and needs a rule against npm's own default; a README with both languages, which doubles the page on npmjs.com.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - The documentation in two languages: how the files are stored (TOR-1179)
- Context: the library is in English only (names, props, built-in texts). Its documentation exists in English and in Brazilian Portuguese (decision of Juliana, TOR-1129).
- Decision (the file pattern): the Portuguese version of `<name>.md` is `<name>.pt-BR.md`, in the same folder. Example: `docs/guide.pt-BR.md` next to `docs/guide.md`. `pt-BR` is the language tag of Brazilian Portuguese.
- Decision (the link between the two): line 3 of each file, under the title, names both languages and links to the other one. The English file has `**English** | [Português](<name>.pt-BR.md)`. The Portuguese file has `[English](<name>.md) | **Português**`. In the two package READMEs the link is the full GitHub address, because npm shows a README outside the repository.
- Decision (covered files): `README.md`, `docs/guide.md`, `docs/releasing.md`, `packages/ui/README.md`, `packages/tokens/README.md`. They are the files a person who uses or releases the library reads.
- Decision (not covered, with the reason):
  - `docs/decisions.md` and `CHANGELOG.md`: a record that grows with every ticket. Two copies would differ soon, and an entry is written once and not read as a guide.
  - `AGENTS.md` and `agent/`: instructions for AI agents. The profile says skill and rule files are in English.
  - `apps/catalog/README.md`, `apps/playground/README.md` and `docs/workflow/`: for people who work on this repository, who read the code and the commits in English.
- Decision (the rules of a translation): the English file is the source. The Portuguese file has the same sections in the same order and the same code blocks, byte for byte. Identifiers, prop names, token names, commands and file paths are not translated. A technical term that Brazilian developers use in English stays in English (for example "build", "token", "Server Component"). A link to a covered file points to the Portuguese version of that file.
- Why: one file next to the other is found without a search, GitHub shows both in the same folder, and a check can pair them by name (TOR-1184).
- Alternatives: a folder for each language (`docs/pt-BR/guide.md`), which separates the two versions and does not fit a package README; one file with both languages, which doubles what a reader scrolls; a documentation site with its own translation system, which is a new tool.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - DataGrid: the mode that edits the table and saves a whole row (TOR-1216)
- Design source: Intraweb's `components/ui/data-grid/data-grid.tsx` (the state `editing`, `drafts`, `rowErrors` and the function `saveAll`, commit `f8ad4c2` of `prontera-e-juno`), its tests, the one screen that uses the mode (`categories-page.tsx`), and the text of the ticket. Figma was not read: this session had no access to it.
- Context: TOR-1216 was added to TOR-1209 after its 6 sub-tickets, so that the library's grid covers all 30 files of Intraweb. It is feature 20 of the entry of TOR-1165.
- Decision: the prop is `onSaveRow(row, changes)`, with the name and the meaning of Intraweb. `changes` has only the changed cells of the row, by the `id` of the column; its type is `DataGridRowChanges` (Intraweb: `RowChanges`). The `onSaveRow` of Intraweb's screen works unchanged.
- Decision: the fields are the `DataGridCellEditor` of TOR-1212, the same component a cell edited by a press shows. So the 4 editors, the changed look and the names of the fields are the same in both ways of editing.
- Kept from Intraweb: the button "Edit table" is shown when the grid has `onSaveRow` and a column has `editor`, and is disabled with no record; in the mode the toolbar has a status, "Cancel" and "Save changes (N)"; the menu of the columns, the buttons of the rows, the selection, the extra row, the arrow of the rows inside a row, the props of a row and the buttons of a group are hidden; a row with a change has the background `bg-warning` and no hover; the row of the open record keeps its own background; a value that is the saved one again is not a change; the rows are saved one after the other; a refused row stays changed and its error is in a row of its own under it (`bg-error`, `text-danger`, an alert); the mode ends when every row is saved; the changed rows are counted over every record, also the ones a filter or a page hides.
- Decision (the error text): the same as for a cell (entry of TOR-1212): `getSaveErrorMessage(error)`, or the message of an `Error`, or `labels.saveFailed`. The text of the row is `labels.rowError(rowLabel, errorMessage)`, with the default of Intraweb: the label, a colon, the text.
- Decision (the texts): 7 new labels with English defaults: `editTable`, `noChanges`, `changedRows(count)`, `cancelEditing`, `saveChanges(count)`, `savingChanges`, `rowError`. The 2 texts with a number are functions, because the plural is a rule of the language.
- Decision (pending): the fields and the 2 buttons are disabled and the button says "Saving…", as in Intraweb. The table also has `aria-busy="true"`. The button is not in the state `loading` of Button (a spinner, and it keeps the focus): the look would differ from Intraweb, and the focus is handled as written next.
- Accessibility problems of Intraweb's mode, fixed here. In each case Intraweb leaves the focus on no element, because the button that was pressed leaves the page or is disabled:
  1. After "Editar tabela": here the focus goes to the first field of the table (to "Cancel" when the page has no field).
  2. After "Cancelar", and after every row is saved: here the focus goes to the button "Edit table".

## 2026-11-15 - Tooltip: shown by CSS, read by a screen reader (TOR-1163)
- Decision: `Tooltip` has the elements and the classes of Intraweb's `Tooltip` (`components/ui/tooltip.tsx`): a `<span class="group/tooltip relative inline-flex">` around the element and the tooltip, the tooltip shown by CSS, and the sides `right` (default) and `top`.
- Accessibility problems of Intraweb's Tooltip, fixed here:
  1. The tooltip has `aria-hidden="true"`, so a screen reader never says its text; Intraweb asks each screen to repeat the text as the `aria-label` of the element. Here the tooltip has `role="tooltip"` and the element gets `aria-describedby` with its id. When the element already has the same text as its `aria-label` (what Intraweb's screens do today), the tooltip is not linked, so nothing is said twice.
  2. Escape does not hide it (WCAG 1.4.13, "dismissible"). Here Escape hides it until the pointer or the focus leaves and comes back.
  3. The pointer cannot move onto the tooltip: it has `pointer-events-none`, and a gap of 12 pixels (WCAG 1.4.13, "hoverable"). Here the tooltip takes the pointer while it is shown, and an invisible strip (`before:`) joins it to the element.
  4. It is shown while the element has the focus after a mouse click too (`group-focus-within`), so it stays over the page after a click until the focus moves. Here it is shown for the keyboard focus only (`group-has-focus-visible`).
- Decision: the hidden tooltip is `invisible opacity-0` (Intraweb: `opacity-0` and `pointer-events-none`). `visibility: hidden` takes it away from the pointer and from a screen reader that reads the page in order, and `aria-describedby` still gives its text to the element. The transition is `motion-safe:transition-[opacity,visibility]`.
- Decision: the element gets `aria-describedby` with `cloneElement`, as Field does for a control. `children` is one element.
- Decision (ticket TOR-1157): the tooltip stays inside the `<span>`, as in Intraweb, and is not rendered in `<body>`. When the pointer or the focus comes, the component measures with `computeAnchoredPosition`: with no room on the side asked for, the classes of the opposite side are used (`left`, `bottom`); when the centered place would leave the window, an inline `top` or `left` moves the tooltip along the element. With room, nothing is written and the classes of Intraweb place it.
- Why not in `<body>`: the tooltip would not be on the page before the JavaScript runs, would need a state for "shown", and its markup would differ from Intraweb's. Limit, accepted: an element around it with `overflow: hidden` cuts it.
- Decision: Escape is heard on the document before any other element (the capture phase), and stops there only when the tooltip was really shown (its computed `visibility`). So with a tooltip shown inside a Modal, the first Escape hides the tooltip and the second closes the Modal; with no tooltip shown, the first Escape closes the Modal.
- Decision: `label` accepts text or elements (Intraweb: text). The exported list of sides is `["right", "top"]`, as in Intraweb.
- Contrast: `text-inverse` on `bg-tooltip` is added to the contrast test of `packages/tokens/src/tokens.test.ts`; it passes in both themes.
- States of the list "States to check": rest and closed (story "Closed"); open by hover and by keyboard focus (stories "Shown By The Pointer", "Shown By The Keyboard Focus"); pressed, disabled, read-only, loading, error, selected: do not apply (a disabled button gets no pointer and no focus, so its tooltip is never shown; the description is still linked); empty: an empty `label` shows an empty box, the app must not render a Tooltip with no text; long content: the text stays on one line (`whitespace-nowrap`), as in Intraweb, so a long text can be wider than the window; near the edge (story "Near The Edge"); right-to-left: considered, not supported, `right` is a physical side; both themes: every story test; reduced motion: the fade is `motion-safe:`.
- Alternatives: `aria-label` set by the Tooltip on the element; the tooltip in `<body>` with `useAnchoredPanel`; a delay before it is shown; Base UI's Tooltip.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - Popover: the panel stays next to its button in the page (TOR-1162)
- Decision: `Popover` has the elements, the classes and the props of Intraweb's `Popover` (`components/ui/popover.tsx`): a `<div class="relative">` that holds a secondary Button and, while it is open, the panel. One rename: `ariaLabel` is `aria-label`.
- Decision: the panel is not rendered in `<body>`. It stays right after the button, as in Intraweb, and is placed with `useAnchoredPanel({ strategy: "absolute" })`, measured from the `<div>` around it.
- Why: with the panel after the button, the Tab key goes from the button into the panel with no code, and the panel needs no focus handling. This is the disclosure pattern of the WAI-ARIA Authoring Practices Guide (a button with `aria-expanded` that shows and hides content). A panel in `<body>` would need the focus moved into it and kept in order by hand, which is the hard part Base UI exists for.
- Limit, accepted: an element around the Popover that hides what leaves it (`overflow: hidden` or a scroll area) cuts the panel, as in Intraweb. ActionMenu is in `<body>` and is not cut.
- Added to Intraweb's behaviour (ticket TOR-1157): the panel opens above the button when there is no room below, and keeps 8 pixels to the left and right edges of the window. Intraweb's panel is always below and can leave the window.
- Accessibility problems of Intraweb's Popover, fixed here:
  1. Escape with the focus inside the panel removes the panel and leaves the focus on no element. Here the focus goes to the button.
  2. The button has `aria-controls` with the id of a panel that is not on the page while the Popover is closed. Here it has `aria-controls` only while the panel is open.
- Difference from Intraweb: the panel lines up with the edges of the button. In Intraweb it lines up with the edges of the `<div>` around the button (`left-0`, `right-0`), which is wider than the button when that `<div>` is a block in a wide container. The position is written as inline `top` and `left` (or `bottom`, `right`) in pixels, not as the classes `mt-2 left-0`.
- Decision: the panel has no role, as in Intraweb. It is not a dialog: it does not take the focus.
- Decision: no `icon` prop. Popover has `"use client"`, and a Server Component cannot give an icon component to a Client Component. `label` accepts elements, so an app puts an icon element in it.
- States of the list "States to check": rest and closed (story "Closed"); open (story "Open"); hover, keyboard focus, pressed: the ones of Button; disabled (story "Disabled"); read-only, loading, error, selected: do not apply; empty: a panel with no content shows its padding; long content (story "Long Content"); near the edge (story "Near The Edge"); right-to-left: considered, not supported, `align` names a physical side as in Intraweb; both themes: every story test; reduced motion: no animation.
- Alternatives: the panel in `<body>` with the focus moved into it; the HTML attribute `popover` with CSS anchor positioning, rejected because the anchor part is not in every browser in use (not verified on the web in this session).

## 2026-11-15 - TabNav: the app gives the current path and the link component (TOR-1143)

- Decision: the current tab is styled by `aria-[current=page]:` classes. Intraweb chooses the classes in its code. This follows the convention that a state is written once, as the attribute a screen reader reads. A test checks that these classes come after the `hover:` classes in the built CSS.

- Decision: the corner of the segmented track is `rounded-[10px]`, the value Intraweb writes. It is not a radius token. No radius token has 10 pixels (`--radius-md` is 8, `--radius-lg` is 12).
- Decision: the fade of the right edge of `primary` is `calc(100% - var(--spacing) * 8)`, 32 pixels. Intraweb writes `2rem`, the same length.

- Alternatives: a hook prop (`usePathname`) given by the app; a `current` flag on each item, computed by the app; the roles `tablist` and `tab` (wrong for links to pages: the WAI-ARIA tabs pattern is for content inside one page); a radius token of 10 pixels.

- Decision: the library has the themes `light` and `dark` only. Intraweb's 3 other themes, `cozy`, `old` and `glass`, stay in Intraweb. Intraweb builds them with the theme function `createTheme` of `@toraline.tech/tokens`, the same way any app builds its own themes.

A theme in the library is a promise to every app: each new component must be checked in it, and each story test runs once for each theme. `glass` also needs CSS rules that are not tokens (below), which the library would have to ship and keep.

Copies of Intraweb's `cozy.css`, `old.css` and `glass.css` are in `packages/tokens/src/intraweb-fixtures/` (commit `f8ad4c2` of `prontera-e-juno`, copied on 2026-11-15). The test reads each copy, gives its values to `createTheme`, and compares every token of the result with the copy. It then builds an app with the 5 themes through Tailwind 4.3.5 and checks the built CSS.
- What the theme function expresses, for all 3 themes:
  - Every color token. `cozy` and `old` give all 59. `glass` gives 16 and takes the other 43 from the light theme (`base: "light"`), as it does in Intraweb.
  - Transparent colors: `rgb(255 255 255 / 0.68)` is a value like any other.
  - The radius sizes: `radius: { md, lg, xl, "2xl" }`.
  - The shadows: `shadows: { sm, card, lg, xl, "2xl" }`. In Intraweb a theme changes a shadow with one CSS rule for each shadow class (`[data-theme="cozy"] .shadow-card { --tw-shadow: ... }`).   - `color-scheme`: it comes from `base` (`light` for `cozy` and `glass`, `dark` for `old`).
- What the theme function cannot express. It gives values to tokens, and these are CSS rules:
  1. `glass`, the gradient behind the page: `[data-theme="glass"] body { background: radial-gradient(...), ..., var(--bg-page); background-attachment: fixed; }`. `--bg-page` is used as a background color, and a gradient is a background image.
  2. `glass`, the blur behind a card: `[data-theme="glass"] .bg-surface:not(input, select, textarea) { backdrop-filter: blur(18px) saturate(1.5); }`. No token holds a blur, and the rule excludes the form fields.
  3. `glass`, the floating parts: `.bg-surface:is(.shadow-lg, .shadow-xl, .shadow-2xl, [role="menu"], [role="dialog"])` gets a less transparent background. It is a second value of `--bg-surface`, chosen by a selector.
  4. `glass`, the fallback: inside `@supports not (backdrop-filter: blur(1px))`, `--bg-surface` is almost opaque. It is a token value inside a condition.
  5. `old` and `dark`, the Tailwind colors of old screens: they give new values to `--color-white`, `--color-zinc-*` and others, so that old screens of Intraweb that use `bg-white` or `text-zinc-700` change with the theme. `createTheme` can write such a value (the key `white` adds `--color-white`), but the value must then be given in every theme of the app, and it is not a token of the design system. It is a temporary help for Intraweb's old screens.
- Proposal for these 5: they stay in Intraweb's own CSS file, next to the output of `createTheme`. The test checks that the 4 rules of `glass`, copied unchanged, build together with the preset of the library: their selectors name the class `bg-surface`, and the library has the same class.
- What would have to change in the library to express `glass` with no CSS of the app. None of it is proposed now:
  - For 1: a token for the image behind the page (for example `--bg-page-image`), and a rule of the preset that puts it on `<body>`. The preset has no rule for `<body>` today.
  - For 2 and 3: a token for the blur of a surface and a token for the background of a floating surface, and components and apps that use a class for "floating surface" in place of `bg-surface`. That is a change in every component that floats (a menu, a dialog).
  - For 4: a field of `createTheme` that writes a second block of values inside a condition (`@supports` or `@media`).
  - Or, for all 4 at once: a field of `createTheme` that takes extra CSS of the theme as text. This was rejected: `createTheme` refuses `{` and `}` in a value on purpose, so that a value an app did not write cannot add a rule (entry of TOR-1005).
- What Intraweb must do when it installs the library, for these 3 themes (not done; it is the work of a later phase): write the 3 inputs in its `theme.config.ts` from its 3 CSS files; remove the shadow rules of `cozy`, `old` and `glass` (the shadows become token values); keep the 4 rules of `glass` and the Tailwind colors of old screens in its own CSS; keep `THEME_DEFINITIONS` and the colors a person chooses (`customColorVars`), which are logic of the app and already use the token names.
- No playground theme and no story were added for the 3 themes. A story would run in the accessibility tests in both themes of the catalog, and `glass` needs its 4 rules to look right. The playground has its own third theme, `paper`, which tests a theme of an app in a real page (entry of TOR-1135).
- Not verified: the 3 themes in a browser, built with the theme function. The test compares token values and built CSS, and does not look at pixels. The contrast of the 3 themes was not checked; Intraweb's files state their own contrast numbers in their first comments.
- Decided by: Juliana, 2026-11-15: the 3 themes stay in Intraweb as app themes. The idea of the library offering more themes of its own is kept in the plan as ticket TOR-1206; nothing of it is built.

## 2026-11-15 - The components are styled with Tailwind CSS 4 classes (TOR-1205)
- Decision: every component of `@toraline.tech/ui` is styled only with Tailwind CSS 4 classes, written in its `.tsx` file the way the app Intraweb writes its components: one text of classes for each variant and each size (`Record<ButtonVariant, string>`). The classes read the tokens through the Tailwind preset of `@toraline.tech/tokens`. The package has no CSS file for a component and no class name of its own. No token was renamed, and the look did not change.
- Why: the approved design says "Components are styled with Tailwind 4 classes that read the tokens". The code gave each component its own class in plain CSS files, and Tailwind was optional.
- Replaces, in the entry of TOR-1006: "the library's component styles are a plain CSS file, with every rule in the cascade layer `components`".
- Replaces, in the entry of TOR-1009: "each component has its own CSS file", "the CSS selects that attribute", "the package does not use `tailwind-merge`", "the app's classes win because of the cascade layer", and the test `styles.test.ts`. What stays from TOR-1009: the lists of variants and sizes, `data-variant` and `data-size`, a state written once as the attribute a screen reader reads, the file `<name>-options.ts`, and the 4 size tokens.
- Replaces, in the entry of TOR-1019: "`peerDependencies` of `@toraline.tech/ui` stay `react` and `react-dom`", and, for `@toraline.tech/ui`, "`exports` gives each CSS file by name".
- Decision: an app's Tailwind builds the classes of the components because of one line in the CSS file of the app: `@import "@toraline.tech/ui/tailwind.css";`. That file has one rule, `@source "../dist";`, which tells Tailwind to read the built files of the package. The app writes 3 lines in all: `tailwindcss`, the preset of the tokens, and this file.
- Why: Tailwind 4 does not read the folder `node_modules`. Its documentation, page "Detecting classes in source files", section "Explicitly registering sources", names `@source` for a library built with Tailwind, with a path relative to the CSS file. With the path inside the package, the app does not write a path into `node_modules`. Checked on 2026-11-15 with the 2 package files of `make pack`, in an app made by `create-next-app` 16.4.6 (Tailwind 4.3.3) and in an app made by `npm create vite@latest` (Vite 8.3.8, Tailwind 4.3.5): the built CSS had the classes of the components. The results are in `apps/catalog/README.md`.
- Decision: `tailwindcss` `^4.0.0` is a required peer dependency of `@toraline.tech/ui`. It stays an optional peer dependency of `@toraline.tech/tokens`.
- Why: a component has no style without Tailwind. The tokens alone (CSS variables, the theme function) work with no Tailwind, for example in the later `packages/native`.
- Not verified: Tailwind versions 4.0, 4.1 and 4.2. Only 4.3.3 and 4.3.5 were run.
- Decision: "style on top" uses `tailwind-merge` `^3.7.0`, a dependency of `@toraline.tech/ui`, inside the helper `classNames`. When two Tailwind classes set the same CSS property with the same Tailwind variant (the part of a class before the `:`, for example `hover:`), only the last one stays, and the app's `className` is last. It is used with no configuration.
- Why: with classes, the order in the attribute `class` does not decide which style wins. The order in the built CSS does, and the app cannot control it. The README of `tailwind-merge` says it supports Tailwind 4.0 to 4.3. It reads any name after the prefix of a color class as a color, and the other token classes have Tailwind's own names, so it needs no list of the tokens. The tests of `class-names.test.ts` check a token class against a token class, against a standard Tailwind class and against a color an app added.
- What changes for an app: a class replaces only a class with the same Tailwind variant. Before, every class of the app won over every style of the library, in every state. Now `bg-red-500` replaces `bg-primary`, and the library's `hover:bg-primary-hover` and `disabled:bg-surface` stay until the app gives `hover:` and `disabled:` classes. CSS of the app that is in no cascade layer still wins. A class of the app inside `@layer components` no longer wins.
- Decision: the class of a state has the Tailwind variant of the attribute a screen reader reads (`disabled:`, `aria-busy:`, `aria-invalid:`, `aria-selected:`, `aria-expanded:`, `peer-checked:`). Which state wins comes from the order in which Tailwind writes its variants, and a test checks that order. One exception: a loading Button leaves out its `hover:` class in the code.
- Why the exception: a class `aria-busy:bg-primary`, which would keep the color while the pointer is over a loading button, would also win over a background the app gave, so a red button of an app would turn purple while it loads.
- Decision: an inner element has the attribute `data-slot` with the name of the part (`data-slot="field"`). It replaces the inner class names `tui-<component>__<part>`, which an app could use in its own CSS.
- Decision: the catalog loads Tailwind CSS 4 with its base styles, as an app does (`apps/catalog/.storybook/preview.css`), and Tailwind reads the source of the components there. The aliases of `apps/catalog/.storybook/main.ts` now name `@toraline.tech/...`; they still named `@toraline/...`, so the catalog read the built files.
- Checked on 2026-11-15, with a temporary Playwright script: the computed style of every element of the 42 stories and of the 2 pages of the playground, in both themes, at rest, with the pointer over each control and with the keyboard focus on each control, before and after. The screenshots are the same, byte for byte, when both sides have Tailwind's base styles. The values that differ draw the same pixels: `translate` and `rotate` in place of `transform` (the thumb of Toggle, the arrow of SplitButton); the animation name `spin` in place of `tui-button-spin`; `border-style: solid` in place of `none` on sides with a border `0px` wide; an outline width of `3px` in place of `0px` on an action of the menu while its `outline-style` is `none`; 4 more shadows with no size and no color in the `box-shadow` of the menu.
- What changes in the catalog only, because it did not load Tailwind's base styles before (an app with Tailwind always had them, and the playground did not change): the spinner of a loading Button is `16px` wide, it was `20px`; the field of Input is as wide as its container, it was `26px` wider; a `<p>` inside a story has no margin.
- Known difference: Tailwind applies a `hover:` class only on a device that has a pointer that can hover (`@media (hover: hover)`). On a touch screen the old CSS kept the hover look after a tap; the classes do not.
- Alternatives: keeping one class for each component, written with `@apply`; a CSS file built in advance with the classes, shipped by the package (no line about sources in the app, and no way for a class of the app to replace one of the library); an `@source` line written by the app with a path into `node_modules`; `clsx` alone, as Intraweb uses for its own components (no class is removed, so the app's class wins only by chance); `class-variance-authority`; a prop for the classes of each inner part (`fieldClassName`).
- Decided by: Juliana, 2026-11-15 (Tailwind classes as Intraweb writes them, no renamed token, no change of look). Every other choice of this entry: agent, to be confirmed in review.

## 2026-11-15 - Choices made in the 6 components (TOR-1010 to TOR-1015)

## 2026-11-15 - Component conventions (TOR-1009)
- Decision: the package uses no library of primitives. A library of primitives is a set of components with behaviour and no styles. A component uses the native HTML element that has the behaviour (`<button>`, `<input type="checkbox" role="switch">`, `<label>`, `<a>`, `<nav>`). Behaviour that HTML does not have (arrow keys between tabs, the menu of the split button) is written by hand, following the WAI-ARIA Authoring Practices Guide. When a later component needs behaviour that is hard to write correctly (a dialog that keeps the focus inside, a select, a combobox, a popup that must move to stay on screen), the library to use is Base UI (`@base-ui/react`).
- Why: of the 6 components of phase 3, 4 need only native elements. The other 2 (tabs, menu button) are short patterns: a few key handlers each. A library would add a dependency to every app for that. Checked on 2026-11-15: `@base-ui/react` 1.9.0, `radix-ui` 1.8.1 and `react-aria-components` 1.22.1 all accept React 19. Base UI is the fallback because it is stable (1.x), has no styles, and its documentation covers every hard component named above. Its menu renders in another part of the page (a portal) and its documentation asks the app to add `isolation: isolate` to its root element; a hand-written menu needs no setup in the app.
- Decision: a variant and a size are declared as an exported list (`buttonVariants`), the type comes from the list, and the component writes them as `data-variant` and `data-size`. A state is written once, as the HTML or ARIA attribute a screen reader reads (`disabled`, `aria-busy`, `aria-invalid`, `aria-selected`, `checked`, `aria-expanded`), and the CSS selects that attribute.
- Why: one class for each element, and no code that builds class names. The look and what a screen reader says cannot differ, because both come from one attribute.
- Decision: when a component's file has `"use client"`, its lists of variants and sizes are in a second file with no `"use client"` (`src/button/button-options.ts`).
- Why: found on 2026-11-15 with Next.js 16.4.6: a Server Component that read `buttonVariants` from the `"use client"` file failed with `buttonVariants.map is not a function`. Next.js lets a Server Component render a component of such a file, but not read its other values.
- Decision: the app's `className` is joined after the library's class with the helper `classNames` (`packages/ui/src/shared/class-names.ts`), on the outermost element. The package does not use `clsx`, `tailwind-merge` or `class-variance-authority`.
- Why: the app's classes win because of the cascade layer `components` (decision of TOR-1006), not because of the order in the attribute. The library's own styles are not Tailwind classes, so there is nothing for `tailwind-merge` to merge.
- Decision: every other prop goes to the main native element, and `ref` is a normal prop that points to it (React 19). No `forwardRef`.
- Decision: `"use client"` is on a file only when the component uses state, an effect or an event handler of its own. The build writes one file for each source file (`preserveModules` in `packages/ui/vite.config.ts`), so each built file keeps or does not keep that line. The entry `@toraline.tech/ui/theme` is now `dist/theme/index.js`.
- Why: with one built file for the whole entry, the line could only be on all components or on none. Checked with Vite 8.3.8: the built `theme/ThemeToggle.js` starts with `"use client"` and the built `shared/class-names.js` does not.
- Decision: each component has its own CSS file in `packages/ui/css/`, and `css/styles.css` imports them. An app still imports only `@toraline.tech/ui/styles.css`. A test (`packages/ui/src/styles.test.ts`) checks every file: layer `components`, class names that start with `tui-`, only level 2 tokens, no raw color, no length in `rem`.
- Decision (the open point of phase 2): spacing and font sizes get level 2 tokens. There are 4: `--text-sm`, `--text-base`, `--text-lg` (font sizes) and `--spacing` (the spacing unit, `0.25rem`). A component writes a padding or a gap as `calc(var(--spacing) * 4)`. The values are the same in both themes. `createTheme` accepts `textSizes` and `spacing`.
- Why: the names are the names Tailwind 4 uses for the same things, which is the rule of TOR-1008. So `text-sm` and `p-4` in an app, and the sizes inside a component, read the same variables, and an app that changes `--spacing` makes its own layout and the components more compact together. One unit, and not one token for each step, keeps the list short. Checked with Tailwind 4.3.5: `p-4` builds to `calc(var(--spacing) * 4)`.
- Decision: these stay plain values in a component's CSS: border and outline widths in `px`, line height, font weight, sizes in `em` or `%`, durations, `z-index`.
- Why: they do not change with the theme, and a token for each would make the list long with no use.
- Decision: one more color token, `--color-danger-hover` (light: `--red-700`, new, `#b42020`; dark: `--red-200`, new, `#f8a3a3`), for a danger button while the pointer is over it. There are now 26 level 2 tokens.
- Why: `--color-primary` already has `--color-primary-hover`. Without a token, the hover color would be computed in CSS and the contrast test could not check it. Contrast of the text on it: 6.63 (light), 9.04 (dark).
- Decision: the template of a component is `packages/ui/src/template/`: a small working component (`Example`) that is type checked, linted and tested with the package, and not exported.
- Why: a template inside `src/` cannot go out of date without a failing check, and its imports work unchanged after the folder is copied.
- Decision: tests press keys with `@testing-library/user-event` 14.6.10 (a development dependency).
- Why: `jsdom` does not run what a key does by default (Space on a checkbox, Enter on a button). `user-event` does.
- Alternatives: Base UI, Radix or React Aria for every component; variant classes (`tui-button--primary`) or `class-variance-authority`; one CSS file for all components; no tokens for sizes, with lengths in `em`; one level 2 token for each spacing step; a template folder outside `src/`.

## 2026-11-15 - Tailwind 4 preset (TOR-1008)
- Decision: the preset is the CSS file `packages/tokens/css/tailwind.css` (`@toraline.tech/tokens/css/tailwind.css`). An app imports it after `tailwindcss`. It imports the tokens and the two themes, declares every level 2 token inside `@theme`, sets `--font-body` as the font of the page, and makes the variant `dark:` follow `data-theme="dark"` with `@custom-variant`.
- Why: Tailwind 4 is configured in CSS. The level 2 names (`--color-*`, `--font-*`, `--radius`, `--shadow`) are the names Tailwind's `@theme` already uses, so each token becomes a class with no mapping: `--color-primary` gives `bg-primary`, `--radius` gives `rounded`. Each class reads the CSS variable in the browser, so `data-theme` changes it.
- Decision: the values in `@theme` are the values of the light theme. A test compares them with `lightTheme`. The shadow alone uses `@theme inline { --shadow: var(--shadow); }`.
- Why: Tailwind copies a shadow's value into the class `shadow` at build time. Checked with Tailwind 4.3.5: with a plain `@theme` the class had the light theme's shadow in both themes. With `inline` the class has `var(--shadow)` and follows the theme.
- Decision: the preset keeps Tailwind's own colors and sizes (`bg-red-500`, `rounded-lg`, `p-4`).
- Why: an app may style on top of a component with any class. Removing Tailwind's defaults would take classes away from the app.
- Decision: a color an app added becomes a class through `createTailwindTheme(themeInputs)`, which returns an `@theme` block with the added colors. The app writes it to a CSS file before the build, together with the output of `createTheme`.
- Why: Tailwind builds classes only from CSS files it reads at build time. A `<style>` element made at request time is too late.
- Decision: `tailwindcss` is an optional peer dependency of `@toraline.tech/tokens` (`^4.0.0`). The tests run Tailwind 4.3.5 through `@tailwindcss/postcss` on the preset and check the classes it builds.
- Known limit: the color classes have the token's name after the Tailwind prefix, so the text colors are `text-text` and `text-text-muted`, and the border color is `border-border`.
- Alternatives: `@theme inline` with a different name on each side (for example `--color-primary: var(--tui-primary)`), which needs a prefix on every level 2 token; a JavaScript Tailwind plugin; one extra `@theme` line written by hand in the app for each added color; `@theme reference`, which is not in Tailwind's documentation.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - Fonts: default stack, and how an app sets its own (TOR-1007)
- Decision: the default fonts are system font stacks, held in the level 1 tokens `--font-stack-sans` and `--font-stack-mono`. The library ships no font file and does not use Montserrat, the font of the old library.
- Why: a system font stack works with no setup and loads nothing. An app that wants Montserrat, or any font, sets it through the theme function.
- Decision: an app sets a font by giving `createTheme` a CSS `font-family` value in `fonts.body`, `fonts.heading` or `fonts.mono`. For a font the app loads with `next/font`, the value is the CSS variable of that font, for example `var(--font-fraunces), Georgia, serif`. The library has no font loading code.
- Why: `next/font` already loads, hosts and preloads the file. The library only needs the name.
- Decision: a test (`packages/ui/src/fonts.test.ts`) reads every CSS and code file of the two packages and fails when a `font-family` is not `--font-body`, `--font-heading` or `--font-mono`, or when a font name appears outside the level 1 files.
- Decision: the playground loads Fraunces with `next/font/local` from a file committed in `apps/playground/app/fonts/` (36,620 bytes, SIL Open Font License 1.1, copied from the npm package `@fontsource-variable/fraunces` 5.3.0).
- Why: `next/font/google` downloads the font from Google at build time. `make check` and the CI would then fail with no network. A local file always builds.
- Decision: an app's themes are built before the build, not at request time. In the playground, `theme.config.ts` holds the inputs and `scripts/write-theme-css.ts` writes `app/theme.generated.css` (ignored by git) before `dev` and `build`. Node 24 runs the TypeScript script directly.
- Why: Tailwind (TOR-1008) reads CSS files when it builds. A color that an app adds can become a Tailwind class only when it is in a CSS file at build time. One generated file keeps the theme values and the Tailwind classes in one place.
- Alternatives: a `<style>` element in the layout, filled by `createTheme` on each request; shipping a default web font with the library; `next/font/google` in the playground.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - Where the theme code lives and how the choice is saved (TOR-1006)
- Decision: the React provider (`ThemeProvider`), the hook (`useTheme`) and the toggle (`ThemeToggle`) are in `packages/ui/src/theme/`, published as the entry `@toraline.tech/ui/theme`. The code with no React (cookie name, `resolveTheme`, `readThemeCookie`, `serializeThemeCookie`, `createThemeScript`) is in `packages/tokens/src/theme-storage.ts`.
- Why: `packages/tokens` stays free of React. The entry `@toraline.tech/ui/theme` starts with `"use client"`, which Next.js needs for code that runs in the browser. A server file (the root layout) cannot call a function from a `"use client"` file, so the functions the server calls are in `@toraline.tech/tokens`.
- Decision: the choice is saved in a cookie, `toraline-theme`, for 1 year, with `Path=/` and `SameSite=Lax`. A Next.js app reads it in the root layout with `cookies()` and writes `data-theme` on `<html>`.
- Why: the server receives a cookie with the request, so the HTML it sends already has the right theme. The browser's `localStorage` is not sent to the server; with it, the server cannot know the theme.
- Cost: reading a cookie in the root layout makes Next.js render every page at request time. For an app that needs pages built once, `createThemeScript` returns a script for `<head>` that reads the same cookie before the page paints.
- Decision: a person who has not chosen gets the app's default theme. The library does not read the dark mode setting of the operating system.
- Why: the tickets do not ask for it, and the server cannot read that setting on the first request.
- Decision: `ThemeToggle` is a `<button>` that goes to the next theme of the app's list on each press. Its accessible name (the text a screen reader says) tells the state: `Theme: dark. Switch to light.`
- Why: an app can have more than 2 themes. The attribute `aria-pressed` can only say "on" or "off", which fits 2 themes only.
- Decision: the library's component styles are a plain CSS file, `packages/ui/css/styles.css` (`@toraline.tech/ui/styles.css`), with every rule in the cascade layer `components` and class names that start with `tui-`.
- Why: a Tailwind class and an app's own CSS both win over a rule in that layer, so an app can style on top with `className`. Phase 3 may change how components are styled; today this covers only the toggle.
- Decision: the test app is `apps/playground` (Next.js 16.4.6, React 19.3.1), private. `make check` builds it, because the root `build` script runs every workspace. The build takes about 4 seconds.
- Decision: Vitest runs browser tests with `jsdom` 31.0.1 and `@testing-library/react` 16.3.3. A test file that needs a page starts with `// @vitest-environment jsdom`.
- Alternatives: `localStorage` with a script (what the library `next-themes` does); a `ThemeScript` React component; a switch with `aria-checked` for exactly 2 themes; Tailwind classes inside the component; `happy-dom` in place of `jsdom`.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - Shape of the theme function (TOR-1005)
- Decision: `createTheme(input)` in `packages/tokens/src/create-theme.ts` returns the CSS of one theme as text: one `[data-theme="<name>"]` block with every level 2 token. The input type is `ThemeInput`: `name`, `base` (`"light"` or `"dark"`, the default theme that gives the missing values), `isDefault`, `colors`, `fonts`, `radius`.
- Why: text works everywhere. An app can put it in a `<style>` element on the server, or write it to a CSS file. The block always has every token, so a theme never depends on which other theme was loaded before it.
- Decision: a color key is the token name without `color-`. A key the library has changes that token. Any other key adds the token `--color-<key>`.
- Why: one rule, and the key maps to the CSS variable letter by letter.
- Decision: `createTheme` throws an error for a name that is not lowercase letters, digits and dashes, and for a value that has `;`, `{`, `}`, `<`, `>`, `\` or `/*`.
- Why: an app may build a theme from values it did not write (for example a color a user picked). Such a value must not close the CSS block or the `<style>` element.
- Alternatives: returning an object of variables for the app to turn into CSS; returning only the values that differ from the default theme; separate fields for changed colors and added colors.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - Token names, token files and the values of the two themes (TOR-1004)
- Decision: the tokens are plain CSS files in `packages/tokens/css/`: `primitives.css` (level 1), `themes/light.css`, `themes/dark.css`, and `index.css`, which imports the three. The same values are TypeScript objects in `packages/tokens/src/` (`primitives`, `lightTheme`, `darkTheme`). A test fails when a CSS file and its TypeScript object differ.
- Why: an app with no build step can use the CSS files as they are, and the theme function (TOR-1005) needs the default values in TypeScript. Writing both by hand, with a test that compares them, needs no generator script.
- Decision: there are 21 level 2 tokens: 16 colors, 3 fonts, `--radius` and `--shadow`. The full list is in `packages/tokens/README.md`. Spacing and font sizes exist only at level 1; phase 3 adds a level 2 token when a component needs one.
- Decision: level 1 names that are not colors are `--space-*`, `--font-size-*`, `--font-stack-*`, `--radius-size-*` and `--shadow-size-*`.
- Why: Tailwind 4 uses the names `--radius-*`, `--shadow-*`, `--text-*` and `--spacing` for its own values. Different names mean a level 1 token never changes a Tailwind class by accident.
- Decision: the purple scale has new numbers, with the old `primary` (`#5e00a1`) as `--purple-500`. The grey scale keeps the old numbers. 5 colors are new (`--purple-50`, `--purple-400`, `--red-300`, `--red-600`, `--green-700`).
- Why: in the old code `purple500` was darker than `primary`, so the numbers were not in order. The new red and green exist because white text on the old red (`#f04848`) has a contrast of 3.67, which is below the 4.5 that accessibility rules (WCAG AA) ask for.
- Decision: in the dark theme `--color-primary` is `--purple-200`, not `--purple-500`.
- Why: `--purple-500` on the dark background has too little contrast to read. A test checks the contrast of 11 text and background pairs in both themes.
- Alternatives: generating the CSS files from TypeScript with a script; keeping the old purple numbers; one `--color-background` token and no `--color-surface-raised` and `--color-surface-muted`.
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - Tooling of version 2 (TOR-1001)
- Decision: npm workspaces as the package manager; Vite 8 in library mode to build the packages, with `tsc` writing the type files; Vitest 5 as the test runner; ESLint 10 with typescript-eslint as the linter; TypeScript 6.0; Node 24.
- Why: npm is already installed and is what the other Toraline repositories use, so nobody installs a new tool. Vite and Vitest share one configuration style, and Storybook (phase 4) can build with Vite too. All five were installed and run on 2026-11-15: build, type check, lint and tests pass.
- Why TypeScript 6.0 and not 7.0: typescript-eslint 8.72 accepts TypeScript below 6.1. TypeScript 7.0.2 exists but the linter does not support it yet.
- Alternatives: pnpm or yarn workspaces (not installed on this machine; the old code had both an npm and a yarn lock file); tsup or tsdown as the build tool; Jest as the test runner (the old code used it through Create React App).
- Decided by: agent, to be confirmed in review.

## 2026-11-15 - The old code moves to legacy/ on the v2 branch (TOR-1000)
- Decision: on the branch `v2`, the old library (Create React App, styled-components 5, Storybook 6) lives in `legacy/` with its own `package.json` and lock files. The repository root is the new workspace.
- Why: npm workspaces need the root `package.json`. Keeping the old `package.json` at the root would install React 18, Create React App and Storybook 6 together with the new packages. In `legacy/` the old code keeps its own dependencies and its own commands, and nothing of it is removed.
- What does not change: the branch `main` still has the old code at the root, and the old package `@toraline/toraline-ui` is still released from `main`.
- Alternatives: leaving the old code at the root and putting the new workspace in a sub-folder.
- Decided by: agent, to be confirmed in review.
